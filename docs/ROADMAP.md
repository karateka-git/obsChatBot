# Дорожная карта Article Bot

## Направление проекта

Личный бот для чтения статей из Telegram. Проект развивается от простого чтения ссылок к Docker-first Python-сервису с SQLite, OpenAI-совместимым LLM-анализом, будущим RAG по Obsidian/GitHub и Codex automation как периодическим интеллектуальным ревьюером. VK рассматривается как будущий дополнительный канал, но не входит в MVP.

Предпочтительное направление:

- Основной сервис: Python.
- Первый канал: Telegram.
- VK: отложить до отдельного будущего adapter.
- Запуск: Docker Compose с самого начала.
- Хранилище: файл SQLite в постоянной папке `data/`.
- LLM: OpenAI-совместимое API через переменные окружения.
- Извлечение текста статей: Python `trafilatura`.
- Будущий RAG: Python-интерфейсы для chunking, embeddings и поиска; SQLite остаётся source of truth.

4. Добавить выбор vault командой
   `/github_vault <repository-url> [vault-path]`:
   - использовать default branch репозитория;
   - использовать корень репозитория, если `vault-path` не указан;
   - разрешать только один активный vault для одного `app_user`;
   - заменять существующее подключение только после подтверждения `да`/`нет`.
5. Добавить команды управления:
   - `/github_status` показывает репозиторий, ветку, путь и время проверки;
   - `/github_sync` немедленно проверяет и синхронизирует vault;
   - `/github_disconnect` после подтверждения удаляет подключение, локальный
     Markdown и поисковый индекс, но сохраняет пользователя, identities,
     статьи, анализы и историю рекомендаций.
6. Хранить подключение vault с привязкой к `app_user_id`:
   - installation и repository IDs;
   - owner, repository, branch и vault root path;
   - HEAD commit SHA, vault tree SHA и ETag;
   - время последней проверки и успешной синхронизации.
7. Загружать Markdown-файлы и сохранять в SQLite:
   - полный Markdown;
   - path и blob SHA;
   - title и frontmatter;
   - tags и wikilinks.
8. Реализовать инкрементальную синхронизацию:

Критерии готовности:

- Пользователь подключает один доступный ему vault без передачи GitHub token в

- Сбой GitHub не мешает обработать статью по уже сохранённым данным.
- Приватные ключи и временные tokens не сохраняются в SQLite и не попадают в
  логи.

## Этап 10. RAG indexing и поиск похожих заметок

Цель: находить связанные со статьёй Obsidian-заметки с помощью гибридного
полнотекстового и смыслового поиска и автоматически сохранять рекомендацию.

Шаги:

1. Разбивать Markdown на chunks по заголовкам, сохраняя heading path, связь с
   заметкой и content hash.
2. Пересчитывать только новые и изменённые chunks.
3. Добавить SQLite FTS5 по title, path, tags, headings и тексту chunk для
   поиска по точным словам и терминам.
4. Добавить embeddings port и OpenAI-compatible adapter для Timeweb AI Gateway:
   - base URL `https://api.timeweb.ai/v1`;
   - отдельный API key;
   - модель `openai/text-embedding-3-large`.
5. Хранить embeddings в SQLite как float32-векторы вместе с model, dimension и
   content hash.
6. Строить запрос к поиску из заголовка и сохранённой LLM-сводки статьи.
7. Независимо выполнять FTS5 и vector similarity search, объединять результаты
   через Reciprocal Rank Fusion и передавать лучшие chunks в recommendation
   prompt.
8. При недоступности embeddings использовать FTS5 как ограниченный fallback и
   явно отражать это в результате.
9. После анализа статьи переводить её в `needs_obsidian_review` и формировать
   типизированную рекомендацию:
   - `add` — добавить новую заметку;
   - `update` — обновить существующую заметку;
   - `skip` — не переносить материал;
   - reasoning;
   - optional target note или название новой заметки.
10. Сохранять рекомендацию с `app_user_id`, article ID и tree SHA vault,
    использованным при поиске.
11. Считать review завершённым сразу после успешного сохранения рекомендации,
    без отдельной команды или подтверждения пользователя.
12. В одной транзакции сохранить рекомендацию, перевести статью в `reviewed` и
    очистить `cleaned_text`:
    - отдельный `content_deleted_at` не добавлять;
    - намеренную очистку определять по `ArticleStatus.REVIEWED`;
    - время завершения review брать из записи рекомендации.
13. При ошибке review сохранить `cleaned_text`, оставить статью в
    `needs_obsidian_review` и записать типизированную диагностическую ошибку.
14. Для повторной ссылки на `reviewed`-статью возвращать сохранённые анализ и
    рекомендацию без повторной загрузки страницы.
15. При явном `/reanalyze` повторно загрузить очищенный ранее источник и открыть
    новый review; неуспешная загрузка не должна уничтожать прежний результат.
16. Оставить GitHub connector read-only: рекомендация сообщает пользователю,
    что добавить, обновить или пропустить, но не изменяет vault автоматически.
17. Оставить FAISS и отдельную vector database опциональными улучшениями после
    измерения реального размера и скорости SQLite-индекса.

Критерии готовности:

- По сохранённой статье приложение находит заметки по словам и по смыслу.
- Результаты FTS5 и embeddings объединяются в одну выдачу.
- При недоступности embeddings остаётся рабочий FTS5 fallback.
- Рекомендация `add`, `update` или `skip` сохраняется и возвращается
  пользователю.
- Успешный review атомарно переводит статью в `reviewed` и удаляет полный
  `cleaned_text`.
- Повторная ссылка использует сохранённую рекомендацию и не скачивает статью
  заново.
- SQLite остаётся source of truth.
- FAISS не требуется для корректной работы.

Этап 9.1 SQLite foundation завершён: добавлены доменные модели и application
ports для разрешённых GitHub installations, единственного активного Obsidian
vault, Markdown-заметок, подтверждений действий с TTL и межпроцессного sync
lease. Начальная схема хранит полный Markdown и frontmatter, нормализованные tags
и wikilinks, source SHA/ETag и timestamps проверки; составные внешние ключи
обеспечивают изоляцию по `app_user_id`. SQLite repositories и тесты покрывают
замену vault, каскадную очистку, обновление заметок, подтверждения и конкуренцию
`tg_catcher`/`vk_catcher` за lease.

Этап 9.2 программный контур GitHub App завершён: добавлена all-or-none
конфигурация App ID, Client ID, slug и PEM; healthcheck проверяет реальную RS256
подпись App JWT. HTTP adapter реализует Device Flow, пагинацию разрешённых
installations и выпуск repository-scoped installation token по REST API version
`2026-03-10`. Общая команда `/github_connect` работает через один in-memory
coordinator на процесс Telegram/VK, возвращает installation URL, Device Flow URL
и одноразовый код, а polling выполняет в background thread. Device code и tokens
не сохраняются и скрыты из `repr`; SQLite получает только installation IDs через
отдельное соединение worker.

Для live-завершения 9.2 осталось зарегистрировать GitHub App, включить Device
Flow, создать PEM и проверить `/github_connect` на реальном GitHub account по
инструкции `docs/GITHUB_APP.md`. После этого следующий программный шаг — выбор
repository и vault path через `/github_vault`.
