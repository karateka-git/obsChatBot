# Журнал решений

## 2026-06-07. Форма проекта

Статус: частично пересмотрено решением "Выбор стека для первой реализации" ниже. Docker-first и итеративный подход остаются актуальными; Kotlin-first больше не актуален.

Решение:

- Развивать проект итеративно, под контролем пользователя.
- Использовать Docker-first подход.
- Первоначально считать Kotlin предпочтительным направлением для основного сервиса, пока лёгкое исследование стека не покажет обратное.
- Считать Codex automation обязательным будущим компонентом.
- Оставить Python как fallback или sidecar для извлечения текста статей и RAG.

Причины:

- Docker-first делает локальную разработку ближе к будущему развёртыванию на VPS.
- Kotlin интересен для изучения и подходит для service orchestration, bot polling, доступа к SQLite и HTTP-вызовов к LLM.
- Python может оказаться сильнее на будущих этапах: article extraction, embeddings и RAG. Поэтому границы модулей должны оставаться заменяемыми.
- Codex automation не должна заменять бота. Она должна периодически ревьюить сохранённые статьи и контекст Obsidian.

Последствия:

- Начинаем с планирования и исследования стека внутри папки проекта.
- Не фиксируем подробную RAG-схему слишком рано.
- Проектируем adapters и services так, чтобы Telegram, VK, automation и будущий RAG могли использовать общую логику обработки статей.

## 2026-06-07. Выбор стека для первой реализации

Решение:

- Выбираем Python как основной и единственный стек первой реализации.
- Выбираем Telegram как единственный канал MVP.
- VK откладываем на будущий adapter.
- Выбираем Docker Compose с начала проекта.
- Выбираем `aiogram` для Telegram polling и отправки ответов.
- Выбираем OpenAI-совместимый Python LLM adapter через переменные окружения.
- Выбираем SQLite через stdlib `sqlite3`, простые SQL-миграции и repository layer.
- Выбираем `trafilatura` для извлечения чистого текста статей.

Причины:

- Python быстрее доведёт MVP до работающего Telegram-бота со статьями, LLM-анализом и SQLite.
- Telegram достаточно для первой полезной версии; VK не должен усложнять стартовый конфиг, архитектуру и критерии готовности.
- `aiogram` закрывает polling и базовую bot-инфраструктуру без ручной реализации Telegram Bot API.
- Python сильнее в извлечении текста статей и будущем RAG, поэтому больше не нужен отдельный Python sidecar.
- stdlib `sqlite3` достаточно прост для начальной схемы; SQLAlchemy можно добавить позже, если запросы и модель усложнятся.

Последствия:

- Этап 2 начинается с Python-каркаса, Dockerfile, `docker-compose.yml`, `.env.example` и минимального запуска приложения.
- Минимальный набор локальных инструментов и Docker-зависимостей фиксируется в `docs/SETUP.md`.
- В MVP нет VK token и VK adapter.
- В коде должны рано появиться интерфейсы для article loading, article extraction, LLM analysis и storage.
- Telegram adapter не должен знать о SQL, LLM-клиенте и деталях извлечения статей.
- Внутренняя модель сообщений остаётся достаточно общей, чтобы VK можно было добавить позже без переписывания article pipeline.
- Подробности исследования зафиксированы в `docs/STACK_RESEARCH.md`.

## 2026-06-27. Миграции до первого MVP

Статус: пересмотрено решением "Пересоздание SQLite на этапе разработки" от
2026-07-20 ниже.

Решение:

- Сохранить реализованный механизм SQL-миграций.
- До выхода первого MVP изменять одну начальную миграцию `0001_initial_schema.sql`.
- После изменения начальной схемы удалять локальную `data/app.db` и создавать базу заново.
- Начать добавлять новые миграции `0002`, `0003` и далее после появления реальных данных, которые нельзя пересоздать.

Причины:

- До реального использования базы начальная схема будет часто меняться.
- Поддержка истории каждой промежуточной версии сейчас не приносит практической пользы.
- Готовый механизм миграций понадобится после появления ценных пользовательских данных.

Последствия:

- До первого MVP локальная база считается временной и может быть удалена.
- Изменения `0001_initial_schema.sql` требуют пересоздания локальной базы.
- После появления реальных данных применённые миграции больше не изменяются.

## 2026-07-20. Пересоздание SQLite на этапе разработки

Решение:

- Пока проект находится в активной разработке, не добавлять последовательные
  миграции `0002`, `0003` и далее.
- При изменении схемы обновлять единственный файл
  `0001_initial_schema.sql` так, чтобы он описывал полную актуальную схему.
- Не создавать технического `Legacy user` в новой базе: таблица `app_users` после
  применения схемы пуста, первого пользователя создаёт только `/register`.
- После изменения схемы удалять локальную `data/app.db` и создавать базу заново
  при следующем запуске приложения.
- Механизм применения SQL-миграций сохранить как часть каркаса проекта, но
  историю промежуточных схем пока не вести.
- Перейти к накопительным миграциям только после отдельного решения о том, что
  в базе появились данные, которые требуется сохранять между изменениями схемы.

Причины:

- Текущая база содержит только данные разработки и может быть пересоздана.
- Поддержка переходов между промежуточными схемами сейчас усложняет разработку,
  не защищая ценные пользовательские данные.
- Одна полная начальная схема упрощает проверку структуры базы Этапа 9.

Последствия:

- Изменения схемы GitHub connector и следующих этапов вносятся в
  `0001_initial_schema.sql`.
- Пересоздание `data/app.db` удаляет все локальные статьи, анализы, пользователей,
  привязки каналов, настройки vault и заметки.
- Перед удалением базы не требуется переносить данные, пока это решение остаётся
  действующим.

## 2026-07-22. SQLite-модель Obsidian vault

Решение:

- Хранить разрешённые GitHub App installation IDs отдельно от подключения
  vault; один пользователь может иметь несколько разрешённых installations.
- Ограничить `obsidian_vaults` одной активной записью на `app_user_id`.
- Хранить полный Markdown и frontmatter заметки в `obsidian_notes`.
- Хранить tags и wikilinks в отдельных связанных таблицах с сохранением порядка.
- Дублировать `app_user_id` в пользовательских таблицах vault и защищать связи
  составными внешними ключами, чтобы SQLite контролировал изоляцию данных.
- Координировать будущую синхронизацию Telegram/VK процессов коротким lease в
  SQLite.
- Хранить ожидающее подтверждение замены или отключения vault в SQLite с TTL и
  одной активной записью на пользователя.

Причины:

- Разрешённые installations принадлежат пользователю, а не одному repository.
- Нормализованные tags и wikilinks пригодны для последующего FTS/RAG без
  повторного изменения формы хранения Markdown.
- Составные внешние ключи не позволяют случайно связать заметку или lease с
  vault другого пользователя.
- SQLite lease работает между отдельными контейнерами `tg_catcher` и
  `vk_catcher`, использующими общий файл базы.
- Подтверждение, начатое в одном привязанном канале, доступно общему incoming-flow
  независимо от процесса adapter.

Последствия:

- Замена или удаление vault каскадно удаляет его локальные заметки и lease.
- Отзыв installation удаляет связанный vault, только если installation
  действительно исчезла из разрешённого пользователю набора.
- Access tokens, device codes и приватный PEM-ключ в этих таблицах не хранятся.

## 2026-07-22. GitHub App authentication runtime

Решение:

- Считать GitHub App connector выключенным, если вся группа GitHub-настроек
  отсутствует, и отклонять частично заполненную конфигурацию.
- Использовать Client ID для Device Flow и для claim `iss` App JWT; App ID
  хранить как обязательный идентификатор регистрации.
- Подписывать App JWT алгоритмом RS256 через `PyJWT[crypto]`, с `iat` на минуту в
  прошлом и `exp` через девять минут.
- Использовать GitHub REST API version `2026-03-10` и
  `application/vnd.github+json` для API-запросов.
- Создавать один in-memory Device Flow coordinator на процесс adapter.
- Выполнять polling Device Flow в daemon thread, соблюдая выданный GitHub
  interval и увеличивая его на пять секунд при `slow_down`.
- Хранить device code и user access token только в памяти. После авторизации
  записывать в SQLite публичные GitHub user ID/login и разрешённые installation IDs
  через новое соединение background thread.
- Выпускать installation access token только по короткому App JWT и при
  необходимости ограничивать token одним repository ID.

Причины:

- Device Flow подходит headless Telegram/VK сервису и не требует callback URL
  или Client secret.
- Отдельное соединение SQLite не передаёт connection входящего сообщения между
  потоками после закрытия request scope.
- Короткие App/installation tokens и скрытый `repr` уменьшают риск утечки через
  хранение, диагностику и исключения.

Последствия:

- `/register` является единым onboarding-сценарием: создаёт пользователя, просит
  имя общего профиля, затем ссылку repository и при необходимости запускает
  Device Flow.
- Имя профиля хранится в `app_users.display_name`, общее для Telegram и VK и
  изменяется командой `/name <имя>`. Внутренний `app_user_id` не показывается в
  пользовательских ответах.
- Отдельные пользовательские команды `/github_connect` и `/github_vault`
  отсутствуют. GitHub-аккаунт является внутренней частью подключения vault.
- Installation URL показывается только после авторизации, если App не установлено
  или не имеет доступных repositories. Если App уже установлено, лишний шаг
  установки пропускается.
- У пользователя приложения есть один активный подключённый GitHub-аккаунт;
  SQLite хранит его публичные GitHub user ID и login, но не пользовательский token.
- Короткий claim активной попытки хранится в SQLite по `app_user_id`, поэтому
  Telegram и VK не запускают две параллельные авторизации одного пользователя.
- После Device Flow проверка исходного repository продолжается в background
  thread через отдельное короткое SQLite-соединение.
- Telegram и VK identities, привязанные к одному `app_user_id` через `/link`,
  автоматически используют тот же GitHub-аккаунт и vault без повторной
  авторизации.
- Ответы `да` и `нет` применяются только к существующему pending-подтверждению;
  без него бот сообщает, что подтверждать нечего.
- Перезапуск процесса удаляет незавершённую Device Flow session; пользователь
  повторно присылает ссылку repository.
- Live-подключение требует зарегистрированного GitHub App, включённого Device
  Flow и читаемого локального PEM.

## 2026-07-22. Повторная отправка ответов в Telegram и VK

Решение:

- Использовать общий sync/async retry-каркас presentation-слоя с тремя попытками
  и коротким экспоненциальным backoff `0.5`, `1.0` секунды.
- Повторять только временные сетевые, rate-limit и серверные ошибки; постоянные
  ошибки запроса, доступа и авторизации сразу логировать без повтора.
- Повторять каждый chunk отдельно, не переотправляя уже доставленные части длинного
  сообщения.
- Для Telegram соблюдать `retry_after`, возвращённый API. Учитывать, что Bot API не
  предоставляет idempotency key для `sendMessage`, поэтому после потерянного HTTP-
  ответа небольшой риск дубликата принципиально остаётся.
- Для VK сохранять один `random_id` на все попытки одного chunk, чтобы повтор был
  идемпотентным со стороны VK API.

## 2026-07-22. Подтверждаемая запись в Obsidian vault

Решение:

- GitHub App получает минимальные разрешения `Contents: read and write` и
  `Metadata: read`.
- RAG формирует конкретное предложение `add`, `update` или `skip` и показывает
  его пользователю до изменения vault.
- GitHub изменяется только после явного ответа `да` на текущее ожидающее
  предложение этого `app_user`.
- Подтверждённые `add` и `update` записываются прямым commit в default branch;
  отдельная ветка и pull request не создаются.
- Перед commit повторно проверяются HEAD и target blob SHA. Конфликт отменяет
  запись и требует пересчёта предложения.
- GitHub является source of truth для vault; SQLite хранит локальную копию,
  поисковый индекс и состояние article/review workflow.

Причины:

- Основная цель проекта — не только рекомендовать изменения, но и создавать и
  обновлять Obsidian-заметки после контроля пользователя.
- Явное подтверждение защищает vault от ошибочного автоматического решения LLM.
- Прямой commit проще для личного vault, чем обязательный branch/PR workflow.
- Optimistic concurrency по SHA не позволяет незаметно перезаписать изменения,
  сделанные пользователем после подготовки предложения.

Последствия:

- Прежнее решение оставить GitHub connector read-only отменено.
- Статья остаётся в `needs_obsidian_review`, пока предложение не подтверждено и
  успешно применено либо не подтверждён `skip`.
- `cleaned_text` очищается только после успешного завершения подтверждённого
  review; ошибка GitHub сохраняет данные для безопасного повтора.
- Первая реализация write-back создаёт и обновляет только Markdown внутри vault
  root и не удаляет заметки.

## 2026-07-23. Выбор repository и корня Obsidian vault

Решение:

- Принимать только HTTPS URL вида `github.com/owner/repository`; branch, query,
  fragment и вложенные GitHub-страницы не являются repository URL.
- Для каждого installation ID подключённого `app_user_id` запрашивать token,
  ограниченный конкретным repository и permission `Contents: write`.
- Читать `repository_id`, канонические owner/name и default branch из GitHub API,
  а каталог vault проверять через Contents API.
- Пустой `vault-path` означает корень repository; непустой путь хранится как
  относительный POSIX path.
- Первый vault сохранять сразу. Другой repository или path сначала сохранять как
  предложение замены с TTL 10 минут и применять только после `да`.
- Не начинать загрузку Markdown в сценарии выбора: первая синхронизация является
  отдельным следующим подэтапом с lease и атомарной фиксацией source SHA.

Причины:

- Пользователь не вводит installation ID, repository ID или branch вручную.
- Repository-scoped write token проверяет итоговое требование приложения:
  GitHub App может читать и записывать именно этот repository. Публичная
  доступность только для чтения не считается достаточной.
- Разделение выбора и синхронизации сохраняет простой атомарный контракт каждого
  application-сценария.

## 2026-07-27. Инкрементальная локальная копия GitHub vault

Решение:

- После первого выбора и подтверждённой замены vault сразу запускать
  синхронизацию; при временной ошибке сохранять само подключение и предлагать
  повтор через `/github_sync`.
- Условно читать HEAD выбранной ветки с `If-None-Match`, затем сравнивать SHA
  дерева именно корневой папки vault.
- Получать полный recursive tree этой папки, хранить manifest по path/blob SHA и
  скачивать содержимое только новых и изменённых `.md` blobs.
- Полностью сохранять Markdown и отдельно извлекать title, frontmatter, tags и
  wikilinks. Отсутствующие в удалённом manifest заметки удалять локально.
- Координировать Telegram и VK через существующий SQLite lease на один vault.
- Фиксировать новый commit/tree SHA и `last_synced_at` только после успешного
  сохранения всех заметок и удаления устаревших путей. При частичной ошибке
  source SHA остаётся прежним, поэтому следующий запуск повторяет снимок.

Причины:

- ETag быстро завершает проверку неизменившейся ветки, tree SHA отсекает commits
  вне vault, а blob SHA исключает повторное скачивание заметок.
- Полный удалённый manifest необходим не только для обновлений, но и для
  обнаружения удалённых файлов.
- Локальная копия остаётся пригодной для будущего RAG при временной
  недоступности GitHub.

## 2026-07-23. Единый реестр chat-команд

Решение:

- Описывать каждую slash-команду одним элементом `ChatCommand`: точное имя,
  подсказка аргументов, раздел справки и пользовательское описание.
- Распознавать команды только через общий `ParsedChatCommand`, не используя
  независимые строковые `startswith`-проверки.
- Генерировать `/help` обходом `ChatCommand` по разделам; строковое представление
  элемента отвечает за одну Markdown-строку справки.
- Обычную отправку URL и контекстные ответы `да`/`нет` описывать рядом со списком,
  но не выдавать за slash-команды.

Причины:

- Имя команды, parser и справка больше не расходятся при развитии проекта.
- Новая команда не может обрабатываться вне реестра и автоматически появляется
  в `/help` после добавления metadata.
- Точное распознавание не путает команды с общим prefix, например `/link` и
  `/link_code`.

## 2026-07-30. Подтверждаемое отключение Obsidian vault

Решение:

- `/github_disconnect` только создаёт подтверждение действия с TTL 10 минут.
- Ответ `да` удаляет активный vault и его локальные Markdown/metadata через
  SQLite cascade; ответ `нет` сохраняет подключение.
- Не удалять GitHub account и installation IDs: отключается конкретный vault, а
  не авторизация GitHub.
- Сохранять пользователя, связанные Telegram/VK identities, статьи, анализы и
  историю приложения. Никогда не изменять удалённый GitHub repository при
  отключении.

Причины:

- Локальный каталог можно восстановить повторной синхронизацией, а удаление
  пользовательских данных или содержимого GitHub было бы несоразмерным действию
  «отключить vault».
- Сохранённая GitHub-авторизация позволяет позднее подключить тот же или другой
  разрешённый repository без лишнего Device Flow.

## 2026-07-30. Ленивая шестичасовая проверка vault

Решение:

- Перед обработкой URL статьи сравнивать текущее время с `last_checked_at`
  активного vault.
- Считать локальную копию свежей строго меньше шести часов; на границе шести
  часов запускать существующую инкрементальную синхронизацию.
- Внутри свежего окна не захватывать lease и не обращаться к GitHub.
- Использовать общий incoming flow, чтобы Telegram и VK имели одинаковое
  поведение.
- Не запускать таймер, scheduler или постоянный polling GitHub.

Причины:
